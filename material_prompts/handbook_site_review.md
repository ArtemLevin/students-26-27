# 7. МЕТОДИЧЕСКИЙ АУДИТ



Оцени страницу глазами ученика соответствующего уровня.



Проверь логическую цепочку:



```text

идея

→ понятия

→ правило

→ визуализация

→ простой пример

→ алгоритм

→ более содержательный пример

→ типичная ошибка

→ самопроверка

```



Не обязательно использовать все блоки, если тема этого не требует.



Проверь:



- понятно ли, зачем вводится формула;

- объяснены ли обозначения;

- не появляется ли формула до объяснения;

- есть ли скачки сложности;

- можно ли повторить тему самостоятельно;

- не слишком ли длинные абзацы;

- достаточно ли визуализации;

- не дублируется ли один и тот же текст в 3–4 блоках;

- выделена ли центральная мысль;

- соответствует ли терминология школьной программе и ЕГЭ.



Особенно ищи места, где сайт выглядит эффектно, но плохо обучает.



Такие места переработай.

# 9. UX/UI REVIEW



Проведи профессиональный интерфейсный аудит.



Оцени:



## Иерархию



- очевиден ли главный объект;

- различимы ли уровни заголовков;

- достаточно ли воздуха;

- нет ли «стены карточек»;

- не конкурируют ли элементы за внимание.



## Композицию



- соответствует ли композиция содержанию;

- нет ли случайной симметричной сетки;

- не повторяет ли страница механически предыдущий урок;

- отличается ли она минимум по трём expression axes от главного reference.



Возможные axes:



- composition;

- density;

- geometry;

- typography;

- accent;

- background art direction;

- signature motif;

- route presentation;

- information hierarchy.



## Анти-AI-slop



Удалить или переработать:



- generic hero;

- бессмысленные gradient blobs;

- purple/indigo AI-style gradients;

- glassmorphism ради красоты;

- случайные glow-эффекты;

- множество одинаковых карточек;

- KPI-like элементы;

- декоративные chips без функции;

- emoji-иконки;

- бессодержательные SVG;

- псевдоаналитику;

- marketing copy;

- лишние animations on scroll;

- чрезмерные border-radius;

- один и тот же shadow на всём.



Страница должна восприниматься как ручная редакционная работа преподавателя.

Если лаборатория существует, оцени её особенно строго.

```text

```



Проверь:



- параметры влияют именно на заявленные объекты;

- формулы пересчитываются корректно;

- точки и линии совпадают с вычислениями;

- диапазоны input имеют математический смысл;

- крайние значения корректны;

- нулевые значения корректны;

- отрицательные значения корректны;

- нет выхода SVG за окно;

- значения округляются разумно;

- десятичная запись понятна русскоязычному ученику;

- reset действительно восстанавливает исходное состояние;

- query/hash modes работают;

- прямой deep link открывает нужный режим;

- переключение режима обновляет UI полностью;

- скрытые панели действительно недоступны пользователю;

- keyboard navigation работает.



Если лаборатория лишь декоративно двигает картинку, переработай её или удали.

# 25. HEATMAP / COMPETENCE MAP REVIEW



Это отдельный критический этап.



Проверь:



- какие competency IDs соответствуют теме занятия;

- нет ли завышения mastery;

- не перезаписываются ли более свежие данные старыми;

- evidence соответствует фактическому занятию;

- ссылка evidence ведёт на правильный section;

- label соответствует компетенции;

- карта и каталог используют одно состояние.



Правило:



**не повышать уровень только потому, что тема была затронута.**



Оценка должна соответствовать наблюдаемому уровню самостоятельности.



Проверь работу localStorage и teacher seed.

Не требуется превращать страницу в benchmark-проект.

- огромные inline SVG;

- многократные event listeners;

- неоправданные timers;

- тяжёлые animations;

- большие layout shifts;

- изображения без lazy loading;

- дорогие blur/backdrop-filter;

- повторные вычисления на input;

- ненужный JS.



Оптимизируй только там, где это даёт реальную пользу.



---



# 29. SECURITY / ROBUSTNESS



Для статической учебной страницы проверь базовые вещи:



- нет `eval`;

- нет `innerHTML` с пользовательским вводом;

- query params не вставляются небезопасно в DOM;

- external `target="_blank"` имеет `rel="noopener"`;

- localStorage parse обёрнут в безопасную обработку;

- динамические данные не создают XSS-поверхность.



---



# 30. CONTENT DESIGN



Перепиши неудачные формулировки, если они:



- сухие;

- слишком длинные;

- повторяют соседний блок;

- похожи на generic AI-text;

- не помогают решить задачу.



Стиль:



- спокойный;

- академичный;

- ясный;

- без маркетинговой интонации;

- обращение на «Вы»;

- короткие содержательные абзацы.



Запрещены фразы:



- «Погрузитесь»;

- «Откройте мир»;

- «Освойте с лёгкостью»;

- «Вы молодец»;

- «У Вас всё получится»;

- любые бессодержательные мотивационные лозунги.



---



# 31. VISUAL REGRESSION



Сравни страницу до и после.



Изменение считается улучшением, если одновременно:



- содержание стало яснее;

- иерархия стала сильнее;

- interaction не сломан;

- нет потери информации;

- mobile не ухудшился;

- кабинет не получил regressions.



Не делай redesign ради redesign.



Принцип:



**минимум бессмысленных изменений, максимум реального улучшения.**



---



# 32. ОБЯЗАТЕЛЬНАЯ БРАУЗЕРНАЯ ПРОВЕРКА



Если доступен Playwright/Chromium, обязательно фактически протестируй.



Проверить минимум:



### Lesson page



- desktop light;

- desktop dark;

- mobile light;

- mobile dark.



### Lab page



- каждый режим;

- минимальное значение slider;

- среднее;

- максимальное;

- reset;

### Home page



- новое занятие;

- карта;

- evidence;

- материалы;

- desktop;

- mobile.



Для каждой страницы:



- screenshot;

- console;

- network failures;

- overflow;

- focus order.



Не считать статический просмотр HTML достаточной проверкой.



---



# 33. AUTOMATED CHECKS



Запусти существующие tests проекта.



Если есть:



- unit tests;

- Playwright;

- dashboard regression;

- accessibility tests;

- lint;

- HTML validation;



выполни их.



Если test падает:



1. выясни причину;

2. исправь regression;

3. перезапусти.



Не отключай тест ради merge.

# 34. ADVERSARIAL REVIEW



После всех исправлений проведи второй проход как критик.



Попытайся найти:



- математическую ошибку;

- неверный знак;

- неправильный координатный расчёт;

- несуществующую ссылку;

- clipping;

- inaccessible button;

- focus bug;

- mobile overflow;

- broken dark theme;

- неправильный evidence;

- дублирующее занятие;

- несинхронный уровень heatmap;

- dead control;

- misleading visual;

- бессмысленный декоративный блок;

- AI-looking section.



Не считай работу законченной до этого второго прохода.



---



# 35. КРИТЕРИЙ ГОТОВНОСТИ



Перед merge должны выполняться ВСЕ пункты:



## Математика



- формулы корректны;

- вычисления корректны;

- примеры корректны;

- графики согласованы;

- SVG согласованы;

- интерактивные вычисления согласованы;

- ОДЗ учтены там, где нужны.



## Методика



- главная идея ясна;

- последовательность логична;

- ученик может повторить тему самостоятельно;

- нет новых случайных тем;

- нет перегруза.



## UI



- один понятный visual leader;

- хорошая иерархия;

- нет AI-slop;

- light/dark работают;

- desktop/mobile работают;

- графика читаема.



## Accessibility



- keyboard works;

- focus visible;

- dialog works;

- labels корректны;

- reduced motion works;

- semantic structure корректна.



## Engineering



- no JS errors;

- no 404;

- no broken links;

- no placeholder;

- no dead UI;

- no horizontal overflow;

- no duplicate IDs;

- no broken imports.



## Integration



- lesson registry updated;

- index updated;

- map evidence updated;

- levels обоснованы;

- old data not corrupted;

- actual PDF/TeX/images linked.

# 36. GIT WORKFLOW



Работай через отдельную branch.



После исправлений:



1. проверить diff;

2. убедиться, что изменены только необходимые файлы;

3. запустить тесты;

4. создать PR;

5. проверить mergeability;

6. проверить CI;

7. устранить failures;

8. merge в `main`.



Если `main` изменился во время работы, сначала синхронизируй ветку и повтори критические проверки.

# 38. ВАЖНЕЙШЕЕ ПРАВИЛО



Не считать страницу качественной только потому, что она:



- красиво выглядит;

- не выдаёт syntax error;

- похожа на reference;

- содержит много интерактива.



Главный вопрос финального ревью:



> Может ли ученик открыть эту страницу без преподавателя, корректно восстановить изученную математическую идею, понять алгоритм решения и использовать страницу без технического или визуального препятствия?



Если ответ хотя бы частично «нет» — продолжай исправление.
