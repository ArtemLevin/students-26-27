# Web Page Design Pipeline — учебная страница ученика

Принятые переменные задаются вызывающим запросом:

DATE=DD.MM.YY

STUDENT=student_slug

STUDENT_DIR=students/STUDENT/site

TEACHER=Лёвин Артём Александрович

Этот prompt задаёт архитектуру проектирования, реализации и проверки учебной web-страницы. Его цель — сохранять уже сложившийся академический, персональный и премиальный характер страниц учеников, одновременно снижая шаблонность и типичные признаки AI-generated UI.

---

## 1. Главная задача

На основе ранее созданных в текущем чате пособия и чек-листа создать автономную интерактивную учебную страницу:

STUDENT_DIR/DATE.html

Если содержание занятия действительно допускает содержательный эксперимент, дополнительно создать:

STUDENT_DIR/DATE-lab.html

Лаборатория релевантна, когда ученик может изменять существенные параметры изучаемого объекта или процесса, наблюдать зависимые изменения, проверять предположения и делать предметный вывод по материалу занятия.

Декоративную, фиктивную или формально добавленную лабораторию запрещено создавать.

Если DATE-lab.html создан:
- в DATE.html разместить заметный переход «Открыть цифровую лабораторию»;
- добавить контекстные deep links возле связанных объяснений, задач или шагов;
- в DATE-lab.html добавить понятный переход «Вернуться к занятию»;
- при наличии нескольких режимов использовать hash или query-параметр и открывать соответствующий режим;
- не дублировать полноценную интерактивную модель внутри DATE.html.

---

## 2. Иерархия решений

При любом конфликте требований использовать следующий порядок приоритетов:

1. учебная корректность и соответствие исходному материалу;
2. понятность ученику и завершённость учебного сценария;
3. доступность и работоспособность;
4. согласованность с существующей страницей ученика;
5. визуальная выразительность и индивидуальность;
6. удобство реализации.

Красивый элемент, ухудшающий чтение, доступность или учебную логику, считается ошибкой.

---

## 3. Источники и неизменяемые ограничения содержания

Единственный источник учебного содержания — ранее созданные в текущем чате пособие и чек-лист.

Разрешено использовать только присутствующие там:
- определения;
- свойства;
- правила;
- методы;
- формулы;
- примеры;
- задачи;
- числовые данные;
- пояснения;
- типичные ошибки;
- выводы.

Запрещено самостоятельно создавать:
- новые условия задач;
- похожие задачи;
- случайные тренировочные примеры;
- дополнительные числовые примеры;
- генераторы задач;
- новые математические, физические или химические утверждения;
- новые ответы, которые нельзя получить из исходного материала.

Допустимо менять способ визуального представления, порядок раскрытия и интерактивную форму при полном сохранении смысла.

Использовать только школьные методы решения.

---

## 4. Обязательный context scan до проектирования

Перед первой строкой HTML изучить:

1. пособие и чек-лист текущего занятия;
2. design-system/REFERENCE_DARYA.md — как текущий контракт визуальной грамматики LEVIN / ATLAS;
3. students/darya_savenkova/site/index.html — как reference уровня navigator-дизайна;
4. students/darya_savenkova/site/14.09.26.html — как reference уровня dated lesson, если создаётся/перерабатывается занятие;
5. pipeline/relevant_docs/relevant.html — как структурный и технический reference;
6. STUDENT_DIR/index.html — как главный источник индивидуальности конкретного ученика;
7. 1–3 наиболее свежие учебные страницы того же ученика, если они существуют;
8. структуру каталогов students/STUDENT/;
9. фактическое наличие PDF, TeX и изображений.

Иерархия reference:
- текущий ученик задаёт индивидуальную идентичность и уже сложившиеся учебные паттерны;
- Дарья задаёт текущую планку качества, editorial/cartographic grammar и связь navigator ↔ lesson;
- pipeline/relevant_docs/relevant.html задаёт инженерный уровень и технические приёмы.

Дарью запрещено копировать пиксель-в-пиксель. Для другого ученика до реализации зафиксировать минимум три оси, которые будут отличаться: composition, accent, density, geometry, typography balance, background art direction, local signature motif, route presentation или information hierarchy.

Файлы искать по реальной структуре репозитория. В типовой структуре:
- students/STUDENT/pdf_docs/DATE.pdf;
- students/STUDENT/tex_docs/DATE.tex;
- students/STUDENT/images/DATE.png;
- students/STUDENT/images/table.png;
- students/STUDENT/table.png.

Нельзя создавать ссылку на файл только потому, что путь ожидается. Сначала проверить наличие.

После context scan кратко определить для себя:
- тему;
- 3–7 ключевых учебных идей;
- главную трудность занятия;
- главный объект визуализации;
- ведущий учебный маршрут;
- существующие визуальные привычки страницы ученика;
- какие решения из последних страниц стоит сохранить;
- какие решения следует специально изменить, чтобы новая страница не выглядела клоном предыдущей.

## 5. Design doctrine

### 5.1. Один визуальный лидер

На каждом основном экране должен существовать один очевидный первый объект внимания:
- ключевая идея;
- центральная формула;
- схема;
- задача;
- интерактивный объект;
- короткий вывод.

Не начинать страницу с симметричной сетки одинаково важных карточек.

### 5.2. Семантика важнее декора

Цвет, размер, рамка, фон, иконка и движение должны сообщать функцию:
- главное;
- правило;
- предупреждение;
- проверка;
- успешный результат;
- действие;
- вторичная информация.

### 5.3. Один объект — один визуальный язык

Один математический или физический объект сохраняет одинаковые цвет и обозначение:
- в тексте;
- формуле;
- SVG;
- графике;
- легенде;
- пошаговом решении;
- DATE.html;
- DATE-lab.html.

### 5.4. Полнота

Нельзя оставлять:
- TODO;
- заглушки;
- «остальное без изменений»;
- фиктивные кнопки;
- неработающие вкладки;
- декоративные controls без действия;
- ссылки на несуществующие файлы.

### 5.5. Проверка предшествует заявлению

Нельзя писать «WCAG пройден», «всё адаптивно», «ошибок нет» или указывать числовой contrast ratio без фактической проверки.

Если проверку выполнить технически невозможно, явно отметить «не проверено в браузере».

SKIPPED, отсутствие Chromium или отсутствие audit-инструмента не считаются PASS.

---

## 6. Визуальная ДНК страниц учеников

Сохранять семейное сходство с уже созданными страницами:

- современный цифровой учебник;
- персональный конспект;
- академическая редакционная эстетика;
- ясная типографическая иерархия;
- спокойная плотность;
- выразительные формулы и схемы;
- качественная тёмная и светлая тема;
- аккуратные границы и поверхности;
- содержательная интерактивность;
- ощущение ручной редакторской работы.

Страница не должна напоминать:
- административную панель;
- SaaS-dashboard;
- корпоративный лендинг;
- интернет-магазин;
- шаблонный каталог курса;
- рекламный landing page;
- набор UI-kit карточек.

Главный текущий визуальный reference — `design-system/REFERENCE_DARYA.md` и страницы Дарьи. Наследовать из них язык: editorial hierarchy, learning-route metaphor, restrained cartographic/scientific imagery, meaningful motion, Navigator symbol when useful, rules/whitespace before cards, and cross-highlight between duplicate views of one learning object.

При этом каждая новая страница должна отличаться от Дарьи минимум по трём expression/fingerprint axes. Точный vermilion accent, расположение фоновых изображений, структура hero и маршрутная геометрия Дарьи не являются обязательным шаблоном.

pipeline/relevant_docs/relevant.html использовать как reference инженерных решений и общего уровня качества. Не копировать его композицию, палитру и набор карточек механически.

---

## 7. Aesthetic direction: выбирать до реализации

Для каждого занятия выбрать одну основную композиционную систему, соответствующую содержанию.

Допустимые направления:

### Editorial theorem
Для теории, доказательств, геометрии, строгих разборов.
Признаки: крупная типографика, заметные формулы, линейное чтение, сдержанные поля, редакционные акценты.

### Workshop notebook
Для алгебры и пошаговых преобразований.
Признаки: последовательность, рабочие заметки, визуальные связи между шагами, локальные callout-блоки.

### Diagrammatic studio
Для графиков, преобразований, координат и визуальных зависимостей.
Признаки: крупная схема или график как композиционный центр, текст работает вокруг визуальной модели.

### Scientific instrument
Для физики, химии и цифровой лаборатории.
Признаки: точные показатели, крупная рабочая область, параметры как инструменты эксперимента, минимальная декоративность.

### Field guide
Для классификаций, свойств, формул и систематизации.
Признаки: разделы как главы справочника, визуальная маркировка типов информации, сильная сканируемость.

Можно создавать собственное направление, если оно лучше выражает тему.

При выборе учитывать последние страницы ученика. Если две последние страницы используют почти одинаковую композицию, текущую страницу построить иначе, сохранив семейную эстетику.

## 8. Anti-AI-slop doctrine

Перед реализацией и перед merge провести отдельную проверку на типичные AI-defaults.

Запрещены как автоматический выбор:

- hero с абстрактным gradient blob без учебного смысла;
- indigo-purple gradient как универсальный «современный» акцент;
- 3–4 одинаковые карточки одинакового веса на первом экране;
- длинная последовательность одинаковых card-grid секций;
- одинаковый radius у каждого элемента;
- один и тот же shadow у всех поверхностей;
- glassmorphism ради эффекта;
- pill/chip для любого короткого текста;
- emoji как иконки или декоративные маркеры;
- псевдографики и декоративные диаграммы без связи с данными занятия;
- бессодержательные progress rings, KPI-cards и dashboard-метрики;
- чрезмерное количество градиентов;
- фоновые сетки, точки и свечения только ради «технологичности»;
- одинаковые двухколоночные блоки во всех разделах;
- CTA-стиль рекламного лендинга;
- текст «Погрузитесь», «Откройте мир», «Освойте тему» и другие generic marketing phrases;
- декоративная лаборатория без исследовательского действия;
- animation-on-scroll для каждого блока.

Emoji в UI не использовать. Для иконок применять компактные inline SVG с currentColor или обычный текст.

Карточка применяется только когда визуальная граница действительно помогает понять смысловую единицу. Не превращать каждый абзац в карточку.

На длинной странице использовать несколько различных композиционных режимов: например редакционный текст, выделенная формула, широкая схема, пошаговый блок, таблица, линия времени, интерактивный модуль. Разнообразие должно следовать содержанию.

## 9. Семантические design tokens

Каждый автономный HTML содержит собственный token block через CSS custom properties.

Использовать семантические роли, например:

--surface-page
--surface-raised
--surface-soft
--text-primary
--text-secondary
--text-inverse
--border-subtle
--border-strong
--accent
--accent-hover
--accent-soft
--success
--danger
--warning
--focus-ring
--shadow-low
--shadow-high
--radius-sm
--radius-md
--radius-lg
--space-1 ... --space-n
--motion-fast
--motion-normal

Компоненты должны использовать семантические tokens. Raw hex, rgb, px для повторяющихся дизайн-значений и случайные локальные цвета внутри компонентов избегать.

Допустимы raw значения там, где это содержательные координаты SVG, вычисляемая геометрия, viewBox, уникальные технические величины или данные задачи.

Если создаются DATE.html и DATE-lab.html:
- использовать одинаковые semantic token names;
- базовая палитра и смысл цветов должны совпадать;
- token block для общей темы копировать согласованно;
- лаборатория может иметь более «инструментальную» плотность, сохраняя ту же визуальную семантику.

Тёмная и светлая темы меняются на semantic layer.

---

## 10. Палитра

Не выбирать цвет случайно из фиксированного списка.

Палитру выводить из:
- темы занятия;
- существующей страницы ученика;
- используемой ментальной карты/изображения, если это уместно;
- выбранного aesthetic direction.

Сохранять спокойный академический характер.

Обычно достаточно:
- нейтральных page/surface цветов;
- одного основного accent;
- 1–2 вспомогательных содержательных цветов;
- success;
- danger/warning.

Акцент использовать дозированно.

Цвет не должен быть единственным носителем смысла.

---

## 11. Типографика

Внешние шрифты запрещены.

Использовать системные стеки. Разрешено сочетать:
- system-ui / Segoe UI / Arial для основного текста;
- Georgia / Cambria / системный serif для редакционных заголовков, если это соответствует выбранному направлению;
- Cambria Math и браузерный математический rendering для MathML.

Требования:
- сильная иерархия заголовков;
- комфортная длина строки;
- крупная ключевая формула или вывод при необходимости;
- минимум декоративного uppercase;
- отсутствие слишком мелкого текста;
- масштабируемость до 200%;
- длинные формулы не ломают layout.

Главный заголовок не обязан занимать весь viewport. Его размер определяется содержанием и композицией.

---

## 12. Первый экран

Первый экран должен быстро дать ученику контекст:
- тема;
- имя ученика;
- преподаватель;
- дата;
- учебная цель;
- главный маршрут или ключевая идея.

Форма первого экрана зависит от aesthetic direction.

Не требуется каждый раз создавать одинаковый hero с:
- крупным h1;
- 4 pill-метками;
- кнопкой;
- декоративной фигурой.

Возможные решения:
- editorial cover;
- крупная формула;
- схема с коротким введением;
- учебный вопрос;
- асимметричная композиция;
- компактная обложка с быстрым переходом к содержанию.

Один элемент должен вести композицию.

Если лаборатория существует, переход к ней должен быть заметен уже в начале занятия или в маршрутной навигации.

---

## 13. Учебная структура DATE.html

Перед практической частью дать достаточную теорию.

Страница должна содержать, когда это присутствует в исходных материалах:
- определения;
- свойства;
- правила;
- смысл обозначений;
- область применимости;
- интерпретацию;
- критерии выбора метода;
- задачи;
- типичные ошибки;
- мини-квиз;
- итоговую самопроверку.

Для каждой основной задачи раскрыть:

1. Что дано.
2. Что требуется.
3. Смысл условий.
4. Графическую, геометрическую, физическую или алгебраическую интерпретацию.
5. Идею решения из 2–5 пунктов.
6. Пошаговое решение.
7. Проверку по исходному условию.
8. Ограничения / ОДЗ / допустимость преобразований при необходимости.
9. Обоснование полноты.
10. Вывод.
11. Ответ.

Для каждого существенного шага объяснять:
- что делаем;
- зачем;
- почему допустимо;
- какое правило используется;
- что означает результат.

Не требуется оформлять каждый пункт отдельной одинаковой карточкой.

---

## 14. Пошаговый режим

Для объёмных решений реализовать stepper или другой понятный progressive disclosure.

Поддержать:
- переход к предыдущему и следующему шагу;
- показ всего решения;
- возврат к началу;
- выделение текущего шага;
- сохранение открытого шага в localStorage, если storage доступен;
- корректную работу без localStorage;
- клавиатуру;
- aria-current или эквивалентное состояние;
- контекстные ссылки в лабораторию, если релевантны.

Не прятать критически важное условие только внутри hover.

---

## 15. Математическое оформление

Raw LaTeX в видимом HTML запрещён.

Формулы оформлять через MathML.

Длинные выражения:
- max-width: 100%;
- локальный overflow-x: auto;
- не создают горизонтальную прокрутку всей страницы.

Ключевую формулу сопровождать текстовым объяснением.

Системы, дроби, степени, корни, интервалы, функции и геометрические обозначения оформлять математически корректно.

---

## 16. Цифровая лаборатория DATE-lab.html

Создавать только при содержательной необходимости.

Лаборатория — самостоятельная рабочая поверхность, а не ещё одна карточка занятия.

На широком экране обычно:
- 60–75% пространства — модель;
- 25–40% — параметры, сценарии, пояснения.

Точное соотношение определяется содержанием.

Подходящие формы:
- координатный график;
- числовая ось;
- геометрическая SVG-модель;
- физическая модель движения;
- таблица знаков;
- динамическая таблица;
- схема преобразований;
- химическая структура/цепочка;
- комбинация нескольких согласованных представлений.

Интерактивность добавлять только там, где она меняет предметно значимое состояние.

Возможности при необходимости:
- drag мышью и касанием;
- pan;
- zoom;
- параметры;
- visibility toggles;
- reset;
- режимы;
- динамические подписи;
- динамический вывод.

Изменения не должны нарушать математическую или физическую корректность исходного материала.

Для геометрии и 3D:
- правильная проекция;
- скрытые линии при необходимости;
- подписи вершин;
- сохранение пропорций;
- reset view;
- доступное управление.

## 17. Связь DATE.html и DATE-lab.html

Переход должен отвечать на вопрос «зачем ученику открывать лабораторию».

Хорошие тексты:
- «Проверить знак на числовой оси»;
- «Исследовать, как меняется график»;
- «Увидеть путь и перемещение»;
- «Проверить зависимость на модели».

Deep link должен:
- выбрать нужный режим;
- подсветить связанные объекты;
- показать цель;
- сохранить понятный путь назад.

## 18. Подсказки

Подсказки добавлять только для реальной сложности.

Нет требования создавать фиксированное количество подсказок.

Каждая подсказка должна:
- объяснять действие или трудный объект;
- открываться по focus и явному действию;
- закрываться Esc;
- оставаться внутри viewport;
- иметь role=tooltip там, где это действительно tooltip;
- не содержать критически важную информацию, недоступную другим способом.

Автоматический показ использовать крайне умеренно. Не отвлекать ученика через несколько секунд после открытия страницы без веской причины.

Пульсации и bounce не использовать как default. Motion должен быть функциональным.

## 19. Интерактивные состояния

Все интерактивные элементы должны иметь применимые состояния:

- default;
- hover;
- focus-visible;
- active;
- disabled;
- loading — если действие асинхронное;
- error — если элемент принимает ввод;
- selected/current — если элемент выбирается.

Не имитировать отсутствующие состояния декоративно.

Destructive actions, если они есть, используют danger semantics. Primary action используется для главного действия, secondary остаётся визуально спокойным.

- сопоставление;
- поиск ошибки;

- объяснение причины;
- возможность повторить;

- клавиатура;

Самопроверка:

## 23. Accessibility contract

Использовать семантические HTML-элементы.

Требования:
- логичный heading outline;
- настоящий button для действий;
- настоящий a для переходов;
- label или доступное имя у input;
- заметный focus-visible;
- логичный Tab order;
- Enter/Space там, где ожидается;
- Esc для закрываемых overlays;
- aria-expanded / aria-controls для disclosure;
- aria-current для текущего шага/раздела;
- aria-live для динамического feedback;
- dialog semantics и управление focus;
- отсутствие clickable div без полноценной клавиатурной модели;
- target size, удобный для touch;
- смысл не кодируется только цветом;
- prefers-reduced-motion.

ARIA использовать только по назначению. Не добавлять aria-label каждому элементу без необходимости, если доступное имя уже задаётся видимым текстом.

- 100%;
- 125%;
- 150%;
- 200%.

## 25. Motion

Motion используется для:
- изменения состояния;
- раскрытия;
- связи между control и объектом;
- перехода шага;
- feedback;
- ориентации по реальному учебному маршруту.

Для LEVIN / ATLAS доступны shared-примитивы из:
`../../../shared/student-dashboard/atlas-motion.js`

Их использовать только по смыслу:
- `data-coordinate-field` — редкие waypoint-точки в подходящем hero;
- `data-journey-stop` + `data-journey-label` — только для реально последовательных вертикальных разделов;
- `data-atlas-parallax="N"` — микропараллакс 0–12 px, обычно 3–7 px.

Не отмечать соседние колонки как последовательные journey stops.

Navigator — минималистичный компасный символ, который может обозначать следующий учебный шаг. Это фирменный знак, без лица, реплик и геймифицированных реакций.

Не использовать постоянное движение как украшение. Координатные точки допустимы только как тихий картографический фон с минимальной амплитудой.

Glow допустим локально для active/focus learning object, преимущественно в dark theme и с низкой интенсивностью. Neon glow, animated gradient borders, blobs, AI-orb и generic particles запрещены.

Обычная длительность переходов — короткая и спокойная. Конкретные значения хранить в motion tokens.

При prefers-reduced-motion:
- убрать bounce, pulse, parallax и waypoint drift;
- сократить или отключить transition;
- сохранить функциональный feedback и изменение состояния;
- контент, который обычно появляется reveal-анимацией, должен оставаться видимым.

## 27. Техническая автономность

DATE.html и DATE-lab.html должны оставаться переносимыми и работоспособными без внешней сети.

Предпочтительно держать page-specific CSS/JavaScript внутри файла. Разрешены стабильные локальные shared-модули репозитория, если они являются частью design/product system и входят в production bundle. Текущий разрешённый пример:
- `../../../shared/student-dashboard/atlas-motion.js`.

Не создавать student-local копию shared-модуля без технической причины.

Внутри каждого файла или доступного локального shared layer:
- CSS;
- JavaScript;
- MathML;
- inline SVG;
- favicon Data URI;
- интерактивность.

Запрещены:
- CDN;
- внешние JS libraries;
- CSS frameworks;
- внешние шрифты;
- remote API;
- remote images;
- удалённые stylesheets;
- обязательный web-server.

Разрешены относительные ссылки на реально существующие локальные материалы.

Файлы должны работать через file://, если браузер не блокирует конкретную стандартную функцию по собственной политике.

Не показывать ученику:
- repository paths;
- debug;
- console output;
- названия внутренних компонентов;
- сведения о pipeline;
- AI/system terminology.

## 29. Objective UX/UI gates

После реализации провести автоматический audit до финального отчёта.

### Gate A — source integrity

Проверить:
- нет удалённых http/https ресурсов;
- нет внешних script src / stylesheet;
- нет raw LaTeX в видимом содержании;
- нет TODO / lorem ipsum / placeholder;
- нет console.log и debug UI;
- нет ссылок на отсутствующие локальные файлы;
- нет дублирующихся id;
- нет emoji в UI;
- нет пустых href;
- нет javascript: URL;
- нет очевидных clickable div/span вместо button/a.

### Gate B — JavaScript

В реальном браузере проверить:
- zero uncaught exceptions;
- zero unhandled promise rejections;
- основные buttons работают;
- tabs/stepper меняют состояние;
- theme switch реально меняет тему;
- quiz даёт feedback;
- modal открывается и закрывается;
- reset действительно сбрасывает;
- storage failure не ломает страницу.

### Gate C — responsive render

Для light и dark theme проверить основные viewport widths.

Проверить:
- documentElement.scrollWidth не превышает clientWidth из-за page layout;
- локальные scroll-контейнеры допустимы для длинной формулы/таблицы;
- fixed/sticky элементы не закрывают ключевой контент;
- controls остаются в viewport;
- текст не обрезан;
- SVG/canvas сохраняют рабочий размер.

### Gate D — accessibility DOM

Автоматически проверить:
- img имеет alt;
- button имеет доступное имя;
- form controls имеют label/name;
- dialog имеет доступное имя;
- disclosure обновляет aria-expanded;
- selected/current state отражается семантически;
- focus возвращается после modal;
- hidden panels не остаются в Tab order;
- keyboard-only сценарий позволяет пройти ключевой flow.

Если доступен axe-core или эквивалентный локальный инструмент, запустить его. Тестовая зависимость допустима; продуктовая страница по-прежнему остаётся автономной.

### Gate E — interaction target and focus

Проверить computed styles в браузере:
- focus-visible действительно различим;
- основные touch controls на мобильном имеют комфортную область нажатия;
- отсутствуют controls размером с мелкую иконку без достаточного hit area.

### Gate F — link integrity

Проверить каждый локальный href/src.
Для DATE.html ↔ DATE-lab.html:
- прямой переход;
- deep link;
- нужный режим;
- путь возврата.

Для PDF/TeX/image:
- ссылка присутствует только при существующем файле.

## 30. Anti-slop audit

После objective gates выполнить отдельный дизайн-аудит.

Это качественная проверка. Не назначать ей выдуманный числовой score.

Проверить:

1. Где первым оказывается взгляд?
2. Можно ли определить тему страницы без чтения всех карточек?
3. Есть ли на первом экране generic SaaS composition?
4. Есть ли повторяющиеся одинаковые cards без смысловой причины?
5. Слишком много ли pills, borders, shadows, gradients?
6. Все ли выделения имеют смысл?
7. Сохраняется ли визуальная иерархия при grayscale-мысленном тесте?
8. Есть ли хотя бы один уникальный содержательный визуальный приём, связанный именно с этой темой?
9. Выглядит ли лаборатория как учебный инструмент?
10. Есть ли section, который можно удалить без потери смысла? Если да — удалить или упростить.
11. Есть ли декор, который можно заменить содержанием? Если да — заменить.
12. Не выглядит ли страница копией предыдущего занятия того же ученика?
13. Не является ли страница прямым клоном Дарьи? Зафиксированы ли минимум три отличающиеся expression axes?
14. Все ли waypoint, route, Navigator, glow и parallax элементы имеют навигационную или учебную функцию?

Для сложной страницы сделать screenshot review минимум:
- desktop light;
- desktop dark;
- mobile 390 light;
- mobile 390 dark.

Посмотреть screenshots целиком, а не только исходный HTML.

В итоговом внутреннем verdict использовать:
- READY — явных проблем нет;
- REWORK — есть заметные проблемы;
- BLOCKED — функциональный/a11y defect.

До merge исправить BLOCKED и значимые REWORK findings.
